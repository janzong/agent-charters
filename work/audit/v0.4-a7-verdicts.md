## 二、发现 20｜`process` 型标题 → workflow 整类丢失

`localstack` 的 `## Development Process` 是**教科书式的 workflow 章节**（先写失败测试 → 找 provider → 查 store → 对照 AWS 文档 → 跑测试 → 迭代），
但 workflow 词表里没有 `process`，0 命中。全库量化：

- 含 `process(es)` / `工作流程` / `開発プロセス` 的标题 **32 个**，其中 **13 个无标签**。
- 无标签的 13 个里可分两堆：
  - **真该是 workflow/流程的**：`Development Process`(localstack)、`Working Process`(KZ-IT-telegram-list)、`Iterative Development Process`(vector)、`Process`(claude-code-ultimate-guide)
  - **不该给任何标签的**：`Inter-process Communication`(proton-drive-sync)、`Main Process`(LobsterAI)、`Multi-process filesystem state`(XcodeBuildMCP)、`Process tree: ps + lsof`(abtop)、FlyEnv 的 `Main/Forked/Renderer Process` 三条
- ⇒ **不能直接加裸词 `process`**（会有 9/13 是误标）。建议只收**限定式**：`development process` / `working process` / `process:` 冒号式 / `工作流程`。

## 三、发现 21｜裸词 `run` 前缀命中 `Runtime`（新）

v0.1.3 把标题通道从子串改成**词首前缀**匹配，当时注明的白名单理由是
"`convention`→Conventions、`test`→Testing 这类复数/派生是有意的"。但 `run` 只有 3 个字母，
`Runtime` / `Runner` 这类**专有名词**也落在词首——实测全库**含 `runtime` 的标题 38 个全部拿到 build_test**，逐个看真正是构建测试的只有 4–5 个：

```
[build_test] cognee        Runtime Flags Worth Knowing      ← 实为 gotchas/environment
[build_test] bug           Runtime Exceptions              ← 实为 structure/style
[build_test] eliza         Runtime architecture            ← 实为 structure
[build_test] LangBot       Runtime Pitfalls                ← 实为 gotchas
[build_test] anda          Runtime Boundaries              ← 实为 boundaries
[build_test] qwengate      Runtime                        ← 不成词
```

- **标签影响**（把裸词 `run` 从 build_test 词表拿掉，511 基座全量重跑）：
  **只有 3 份掉 build_test** —— `DeepTutor`、`agentsmith`、`onlook`，逐份看过**三份都是假阳性**
  （`onlook` 是 `### Stack & Runtimes`；`agentsmith` 是 `## How Sessions Run`＝workflow；
  `DeepTutor` 的 `# Run any capability` 本身还是逃逸出来的代码注释）。
- ⇒ 结论：`run` 这个标题词**precision ≈ 12%（4–5/38）、remove-cost = 3 份且全错**。
  与 v0.1.3 删裸词 `make`（12 份 7 错）是同一形态，建议同法处理：
  换成 `run tests` / `running` / `how to run` / `run the` 等限定式，或对 `runtime` 加否决。

## 四、发现 16 的标签影响面（本批第一次量化）

本批 `noaadata` 是发现 16 的"标签被污染但不掉"的样本，正好促使把"现象面"和"标签面"分开量：

| 口径 | 文件数 |
|---|---|
| 围栏逃逸守卫被触发（标题密度 ≥3 误判） | **86 / 558** |
| 其中围栏内确有 shell 注释壳（`#` + 小写词 / `#!` / `#===` / 含命令词） | **66** |
| 其中围栏内全是 Title-Case 短语、守卫**应当**保留（如 `mpp` 的嵌套围栏） | **20** |
| **修掉之后会掉标签**（两种修法交叉验证） | **15–18 份，各掉 1 个标签，无一例新增** |

- 两种独立修法的结果收敛，说明数字不是修法artifact：
  - 修法 A「看围栏信息串」：` ```bash/sh/python/... ` 一律按代码块，只有 `` ```md/mdx `` 或无标记才走密度守卫 → **掉 15 份**
  - 修法 B「看注释壳」：围栏内有 `#`+小写词/命令词 → 一律按代码块 → **掉 18 份**
- 掉的标签集中在 **environment（8–9 份）** 与 **style（3–4 份）**，正是 v0.1.6 注释里点名的
  `# Install` → build_test、`# Writing Style` → style、`# Rules` → boundaries 三个假通道。
- 抽查 2/2 全是真错：`78/xiaozhi-esp32` 的 style 来自 ```sh 块里的 `# Format/check touched files`；
  `alibaba/MNN` 的 environment 来自 ```bash 块里的 `# Common CMake options: ...`（`cmake` 命中）。
- ⇒ 建议落地修法 A（**看语言标记**）：判据更硬、不依赖对注释内容的猜测，
  且天然保住 `mpp` 那 20 份格式不良嵌套围栏（它们是 ` ```mdx ` 开头）。
  预期 `environment` −8~9 份、`style` −3~4 份。
