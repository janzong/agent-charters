# 分母研究：AGENTS.md 这类「写给 AI 的书面规约」到底有多普遍（2026-09-18）

**要回答的问题**：本项目此前**所有百分比都是框内率**（分母＝"有 AGENTS.md 的那 558 个仓库"），
从来没有过一个**生态率**。这份研究补上分母。设计先写好并冻结在 `plan-prevalence.md`（预登记），
本文是执行结果——**包括预登记判据落空的那一条**。

**一句话结论**：`AGENTS.md` 是**活跃仓库的习惯（6.2%）**，不是**仓库总量意义上的普及（1.0%）**；
它比同类格式（`CLAUDE.md` 5.4% / `copilot-instructions` 1.1% / `.cursor/rules` 0.7%）不占压倒性优势，
但也不是早期采纳者的孤例。

```
                    n        AGENTS.md         95% CI          CLAUDE.md
活跃仓库（框A）      817       6.2%        [4.8,  8.1]          5.4%
活跃仓库加权后       817       4.6%        （粗估，见 §4.3）        —
活跃仓库（框B）       57       1.8%        [0.3,  9.3]          0.0%
全部公开仓库         924       1.0%        [0.5,  1.8]          1.2%
非 fork 非 archived  627       0.5%        [0.2,  1.4]          0.6%
```

口径：`pushed:>2026-06-20`（近 90 天）、`fork:false`、`archived:false`；文件判定走
`GET /repos/{r}/git/trees/HEAD?recursive=1`（**递归**，看得见 `docs/AGENTS.md`）。
seed `20260918`，两项全部可复算。

## 3. 方法（以及和预登记不一致的地方，逐条列出）

**框 A｜活跃 + 趋势（主）**：2010..2026 **每年随机取一个切片**，查
`created:<切片> pushed:>截止日 fork:false archived:false`，**分页取尽**（避免 best-match 排序偏差），
切片内**随机抽 50** 查树。

**框 B｜存量（无偏）**：ID 空间 `[1, 1375203308]` 上均匀抽样（上界由二分探测坐实）。
实测命中率 **35%**（其余是已删/私有）⇒ 1000 个有效样本探了 **2920** 次。

**与预登记的偏差（4 条，都是执行中被动改的，不改结论方向）**：

1. **切片粒度自适应**。预登记说"某个切片 `total_count>1000` 就换更小切片"。实际：2026 年一周有
   **62,582** 个活跃仓库，日也超 1000 ⇒ 收敛到**随机一小时**。最终粒度：2010–2017 = 周，
   2018–2022 = 日，2023–2026 = 时（表里逐行标注）。
   *代价*：不同世代切片的"空间尺度"不同，世代间的比较要打折。
2. **采样量**：`--per-gen 50`（预登记原值）。2010 那周只有 22 个活跃仓、2023 那小时只有 46 个 ⇒
   抽到全量（22 / 46），不是故意的，是切片里就这么点。
3. **两条口径的 `truncated`**：递归树在 ~10 万条目处截断，命中 3/817（0.4%）。
   主指标**含/剔都报**：含 51/817 = 6.24%，剔 51/814 = 6.27%。
4. **新发现的问题类：单仓 403 封禁**。GitHub 对**个别仓库**返回
   `403 {"message":"Repository access blocked","block":{"reason":"tos"}}`——不是限流，不是 404。
   第一版把它误判成次级限流，导致反复退避、白卡几十分钟。现已单列一类（框 B 里命中了 1 个）。
   **教训**：`403` 有三种含义（主限流 / 次级限流 / 单仓封禁），必须读 body 才能分开。

**限流实况**（也会影响别人复算）：GitHub **要求同一用户串行请求**——3 线程并发就会持续 403；
串行 + 连接复用（`requests.Session`）跑满 ~8 次/秒无碍。框 A ≈ 1,020 次调用、框 B ≈ 3,900 次，
分开跑，全部缓存到 `data/cache/prevalence/`（gitignore），重跑零成本。

## 4. 框 A 明细（活跃率 + 趋势）

### 4.1 主指标

817 个可判定仓库（818 抽样 − 1 个 HTTP 404）：

| 格式 | 命中 | 占比 | 95% CI（Wilson） |
|---|---|---|---|
| `AGENTS.md` | 51/817 | **6.2%** | [4.8, 8.1] |
| `CLAUDE.md` | 44/817 | **5.4%** | [4.0, 7.2] |
| `.github/copilot-instructions.md` | 9/817 | 1.1% | [0.6, 2.1] |
| `.cursorrules` / `.cursor/rules/*.mdc` | 6/817 | 0.7% | [0.3, 1.6] |

**交叉表**：`AGENTS.md ∩ CLAUDE.md` = 18 个；**只有 `CLAUDE.md`** 的有 26 个。
⇒ 在野外，**P(CLAUDE.md | AGENTS.md) = 35.3%**。

这条和我们语料库里的同名数字（**59.1%**，285/482）差了 **1.7 倍**——
量化了语料库的一个偏差：**我们的 558 仓偏向"装了好几个工具的仓库"**（见 §6）。

⚠️ **但这条判据在这份数据上不可用，别引用它的结论**：世代与**仓库年龄**完全混淆——
"2010 年建的仓、今天还在 push"是**幸存者**（被筛过一轮的项目），而 2026 年那批里塞满了刚建的个人仓。
所以"老世代比例高"既可能是"老项目更成熟所以写了章程"，也可能是"老仓活下来的都是重型项目"，
**这两个机制这份数据分不开**。要分开得做"同一日历年的不同年龄 cohort"或读提交历史看
`AGENTS.md` 的**加入时间**（贵，未做）。⇒ 趋势这一项，**本次只交付"没测出来"，不交付"没在扩散"**。

### 4.3 世代权重的影响（为什么 6.2% 和 1.8% 能差这么多）

框 A 每个世代等权（各 ~50 个），但**总体里各世代的数量极不均匀**：把每个切片按粒度年化
（周 ×52 / 日 ×365 / 时 ×8760），活跃仓数从 2010 年的 ≈1.1 千涨到 2026 年的 ≈476 万。
按年化活跃仓数**加权**后：

```
世代等权（框 A 主口径）  51/817 = 6.24%
按年化活跃仓数加权（粗）         ≈ 4.63%
```

⇒ 主口径 6.2% 里混了"老世代被等权放大"的成分。**年化是单切片外推，噪声极大**，
只用来说明方向：**总体加权的真值应落在 6.2% 的下方**。

## 5. 框 B 明细（存量率，无偏）

上层抽样：id 上界 **1,375,203,308**（二分 31 次探测）｜探 2,920 次 → **1,011 个存在**
（命中率 35%）｜树拉取：**924 拿到**（84 个 `409`＝空仓、3 个 `404`）。

| 子总体 | n | AGENTS.md | 95% CI | CLAUDE.md |
|---|---|---|---|---|
| 全部公开仓库 | 924 | 9 = **1.0%** | [0.5, 1.8] | 11 = 1.2% |
| 非 fork | 632 | 3 = 0.5% | [0.2, 1.4] | 4 = 0.6% |
| 非 fork 非 archived | 627 | 3 = 0.5% | [0.2, 1.4] | 4 = 0.6% |
| 近 90 天有 push（含 fork） | 65 | 2 = 3.1% | [0.8, 10.5] | 3 = 4.6% |
| **活跃（非 fork 非 archived + 90 天）** | **57** | 1 = 1.8% | [0.3, 9.3] | 0 |

**生态成分（顺手测出来，本身有价值）**：
- **fork 占 29%**（`repositories/{id}` 层面的 `fork:true`）
- archived 占 1%
- **近 90 天有 push 的只占 7%** ⇒ 存量里 **93% 是"死"的**
- **8.3% 是空仓**（`409 Git Repository is empty`，有仓无提交）

**两个框在活跃率上不一致**：6.2%（框 A，n=817）vs 1.8%（框 B，n=57）。
框 B 的 CI [0.3, 9.3] 包得住 6.2%，即**统计上不矛盾**，但框 B 的 n 太小、没有分辨力。
机制上我倾向认为**真值在两者之间偏低处**：框 B 是**总体加权**（ID 均匀抽样被近年新建仓支配，
而世代表里近年比例并不高），框 A 的 6.2% 是**世代等权**（§4.3 加权后 4.6%）。
**要把框 B 的活跃子样本提到 n≈300，得再探 ~12,000 个 ID（约 2 小时）——本次没做，记账。**

**9 个存量命中里 7 个落在"近 90 天没 push"的仓库**（另 2 个在活跃桶）。
⇒ 按数量看，**野外的 AGENTS.md 相当一部分是"墓碑"而不是"现行实践"**（n=9，只能说方向）。

## 6. 对项目主张的影响（该软化的 / 站得住的）

**站得住的**：
- `AGENTS.md` 确实是被采用最多的那一类（6.2% vs 同类 0.7–1.1%），**同类格式甩开一个量级**——
  这是一个**测出来的**、不是判断出来的选择依据。
- 语料库的**框内率**说法（92%/70% 等）不受影响：分母没动，只是从此知道**分母外面有多大**。

**该软化的**：
- ❌ "AGENTS.md 是主流工程实践" / "生态"——**1.0% 存量率不支持**。措辞上限是
  "**活跃项目里的一个真实习惯**"。
- ❌ "`CLAUDE.md` 只是伴生文件（59.1%）"——那是**条件在"有 AGENTS.md"**上的条件率；
  无条件率是 **5.4% vs 6.2%**，**基本并驾齐驱**。以后引用 59.1% 必须带条件。
- ⚠️ "格式正在普及"——**本次没测出来**（趋势判据因年龄混淆失效，§4.2）。
- ⚠️ `P(CLAUDE|AGENTS)`：语料库 59.1% vs 野外 35.3% ⇒ 语料库偏向"多工具重型仓" 1.7 倍。

## 7. 弱点 / 不可测（预登记时就写下，事后不补理由）

1. **ID 抽样偏向"存活下来的仓库"**，且组成以新仓为主 ⇒ 已同时报**未条件化**（1.0%）与
   **条件化**（活跃 1.8%）两个数，没有只报好看的那个。
2. **看不见私有仓库**（企业内部可能更多也可能更少）——只能标注，不能解决。
3. **"有文件" ≠ "文件有用"**。本研究只回答普及度，不回答有效性（那是另一个实验，也是判据 6 缺的那块）。
4. **搜索切片是"准随机"**（分页取尽后切片内随机），不是数学意义的无偏；世代趋势用它够，存量率不用它。
5. **单仓 ToS 封禁**（403 `Repository access blocked`）不可判别，只能单列。
6. **`truncated` 的 0.4%** 超大仓看不见深层，含/剔都报过了。
